### 2. `in1~in5` 下平台故障隔离

| 动作 | 故障注入 | 期望设备状态 | 期望业务状态 | 结果 | 证据 |
|---|---|---|---|---|---|
| `in1` | 动作失败或超时 | 下平台隔离，不进入整机维护 | 上平台继续加热和售卖；新补肠被阻断 |  |  |
| `in3` | 动作失败或超时 | 下平台隔离，不进入整机维护 | 上平台继续加热和售卖；新补肠被阻断 |  |  |
| `in4` | 动作失败或超时 | 下平台隔离，不进入整机维护 | 上平台继续加热和售卖；新补肠被阻断 |  |  |
| `in5` | `IR_THROW_FAILED` | 下平台隔离，不进入整机维护；批次保留 `requiresManualConfirm=true` | 上平台继续加热和售卖；自动补肠停止，运维清理滚筒/升降台/下平台后人工确认恢复 |  |  |
| `in5` | 非红外残肠类普通失败 | 下平台隔离，不进入整机维护 | 上平台继续加热和售卖；新补肠被阻断 |  |  |

通过标准：

- `onlineStatus` 不变为 3。
- `errorStatus` 不因下平台隔离故障变为整机故障。
- `lowerPlatformStatus=ISOLATED` 或等价下平台隔离状态上报到后端。
- 首页/下单口径仍允许售卖已有可售烤肠，但不能继续依赖下平台补新肠。
- `in5 / IR_THROW_FAILED` 不允许静默跳过当前目标，必须保留人工确认门禁；人工确认前不得恢复自动补肠。

### 5. MQTT ACK 与 HTTP 兜底

| 场景 | 操作 | 期望 | 结果 | 证据 |
|---|---|---|---|---|
| MQTT 正常 ACK | 正常执行一次补肠动作 | 后端返回 `action_group_telemetry_ack`，Android 移除 pending |  |  |
| ACK rejected | 模拟后端持久化失败或 rejected ACK | Android 保留 pending，并触发 HTTP fallback，不立即丢事件 |  |  |
| MQTT 断开 | 执行动作期间断开 broker | Android pending 不超过上限，重连或 HTTP fallback 后后端可查事件 |  |  |
| HTTP 慢响应 | 延迟 HTTP fallback 响应 | Android 不阻塞动作主链路，后续仍可重试或收到 ACK 后清理 |  |  |

## 1000 台在线容量口径

| 检查项 | 期望 | 结果 | 证据 |
|---|---|---|---|
| MQTT 主题与消息体 | 单设备消息独立携带 `deviceId/deviceCode/eventId`，不依赖全局共享状态 |  |  |
| Redis key | key 包含设备维度和事件维度，避免多设备覆盖 |  |  |
| pending 上限 | Android 单机 pending 有上限，异常时不无限增长 |  |  |
| 持久化去重 | 后端按设备 + eventId 去重 |  |  |
| 后台查询 | 查询默认分页，不一次性拉取全量动作事件 |  |  |

## 失败判定

出现任一情况，本轮验收失败，必须回代码修复后重新验收：

- `in1~in5` 下平台故障导致已有上平台烤肠停止烤制、保温或售卖。
- `in6/in7/out*` 故障被错误降级，导致可能存在未知烤肠位置仍继续营业。
- `in2 / IR_PICK_FAILED` 后批次仍被 `requiresManualConfirm=true` 卡住。
- 动作事件在 MQTT rejected ACK 或 HTTP fallback 后不可恢复地丢失。
- `in2/in7/out1` 物理状态与本地烤肠箱、烤盘、后端快照不一致。
- 后端无法通过动作轨迹页面定位动作、错误码、箱号、烤盘号、物理检查点。
