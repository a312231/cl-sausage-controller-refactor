# 营业结束收口最小加固设计

## 目标

只收口独立审核确认的两个阻断问题，并保证营业结束收口卡住后，管理员可以通过维护页现有“丢弃所有烤肠并重置烤盘”或“清空烤盘”完成接管，再点击“恢复正常状态”回到正常运行。

## 边界

- 只识别 `source=营业结束丢弃` 的 DiscardJournal，不改变普通过保丢弃、订单出餐、补肠、搬盘或其他动作恢复。
- 不新增线程、协程作用域、Timer、Executor、锁、后台重试或常驻资源。
- 不在 `faultHeatTransitionLock` 内主动探测 Modbus，不增加串口轮询。
- 不修改后端、MQTT/HTTP 协议、下位机指令、支付或订单逻辑。
- 人工按钮本身代表管理员接管，不再针对目标烤盘追加“已丢弃/未丢弃”的二次问答。

## 修复一：营业收口保持停热

营业收口仍先执行现有 `pauseBusiness()`，三区写 0 全部成功后才开始丢弃。

`discardSausage(..., businessCloseout=true)` 成功后不调用通用 `refreshTemperatureAfterStablePanMutation()`；其他丢弃来源保持原行为。这样剩余烤肠不会在停业期间重新触发烤制或保温温度，也不会为每根营业收口丢弃增加三区 Modbus 写入和状态锁占用。

## 修复二：断连竞态最小门禁

保留每盘丢弃前现有真实 `connectStatus()` 检查。在机械认领和 `COMMAND_INTENT` 准入阶段只读取当前 Modbus master 是否存在的非阻塞快照：快照不可用时拒绝认领或准入，并在命令下发前释放已认领资源。

不把 `connectStatus()` 放入状态锁，因为它会主动访问串口。若 master 仍存在但物理链路在写入时才中断，继续使用现有“结果不确定则保留 journal/owner/moveStatus 等待人工恢复”策略。

## 人工恢复

维护页现有两个人工入口只可接管营业收口自身的丢弃残留：

1. 先复用现有异步机械空闲检查；UI 线程不阻塞，也不创建新线程。
2. 空闲证据通过后，如果仅存在 `source=营业结束丢弃` 的 journal，则原子清理对应 owner、journal 和 `moveStatus=4`，并把该目标盘视为已由管理员接管。
3. “丢弃所有烤肠并重置烤盘”继续执行现有剩余烤肠丢弃与盘位重置；“清空烤盘”继续执行现有全盘数据清理。
4. 全盘清空后只做最小运行态收口：耐久写入 `modeType=1`、`transitionMode=0`、`highConcurrencyResidualDrain=0`，清除 `closeoutPending`；保持维护态、故障态和 `isEnable=0` 不变。
5. 管理员随后点击现有“恢复正常状态”；现有故障恢复流程负责检查 Modbus 并恢复设备状态，管理员再按既有流程开启算法。

人工接管失败时不清理 pending 或其他业务证据，仍可再次点击按钮重试。

## 测试与验证

- 先增加失败测试，证明营业收口丢弃不会刷新正温、非营业收口丢弃仍会刷新。
- 证明 master 快照不可用时，机械认领和命令准入均拒绝且不写 `COMMAND_INTENT`。
- 证明人工入口只接管营业收口 journal；其他来源和非空闲状态继续拒绝。
- 证明人工清盘完成后低并发三字段与 pending 耐久收口，但不擅自清除故障或开启算法。
- 运行针对性测试、Debug/Release 单元测试和 `git diff --check`。本地测试不代表真实 RS485、Modbus 或机械验证。
