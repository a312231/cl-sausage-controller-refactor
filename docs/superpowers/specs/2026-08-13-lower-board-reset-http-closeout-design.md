# 下位机复位与订单自动收口设计

## 目标

解决两类问题：

1. 普通“下位机复位”按钮在机械忙、订单中或寄存器非空时无法点击；
2. 复位中断订单后，上位机的订单、`moveStatus`、session、owner、资源锁或后端工作锁残留，导致首页卡住或后续顾客无法下单。

本设计保留已经完成的“下平台 `in1~in3` 半故障安全收口”切片，不回改其 `in4` 物理安全边界。

## 已确认的按钮职责

### 普通“下位机复位”

- 任何时候都可以点击，不再读取 `moveStatus`、201、203 或动作结果寄存器作为拒绝条件。
- 向下位机写 `999=1`，由下位机清寄存器并让机械结构回到初始位置；上位机不逐个写寄存器 0。
- 不改变原有业务状态和故障状态：运营中仍是运营中，维护中仍是维护中，休息中仍是休息中；不清 `errorStatus`、下平台隔离、算法开关或其他已有故障原因。
- `onlineStatus=4` 是订单执行中的临时状态。若复位终止了该订单，按现有订单收口规则退出 4：无已有故障时回到运营中，有已有故障时保持/进入维护；这不等于普通复位主动切换营业模式。
- 复位成功后只进行一次 App 冷重启，用来彻底终止旧订单协程和旧机械任务。

### “紧急复位”

- 同样不做忙闲检查，写入同一个 `999=1`。
- 用于严重故障，保留现有“进入/保持维护、封禁机械命令、等待人工检查”的语义。
- 订单终止、资源释放和退款规则与普通复位共用同一套收口逻辑，避免两套实现再次分叉。

### “检查并恢复设备”

- 是唯一允许清除真实故障状态、解除下平台人工恢复阻断并把维护中恢复到运营中的入口。
- 普通复位不会替代该按钮，也不会静默解除原有维护或故障。

## 普通复位流程

### 1. 点击后立即临时禁售

上位机复用一个单槽 `ResetCloseoutRecord`。订单被接受时先写入 `ORDER_ACTIVE` 阶段并持续记录 `out4` 成功数量；没有订单时点击复位则直接新建记录。记录只包括：

- `resetId`、复位类型、开始时间、原业务状态和原 `orderBlockReason`；
- 当前订单号（如有）；
- 每个订单项的总数量和已确认 `out4` 成功数量；
- 阶段：`ORDER_ACTIVE`、`PREPARED`、`RESET_WRITTEN`、`SERVER_CLOSED`。

随后把 `orderBlockReason` 临时设为 `SYSTEM_RESET_IN_PROGRESS`，刷新首页并同步后台，使二维码隐藏、支付入口拒单。原 `orderBlockReason` 保存在记录中，结束时原样恢复，不会被复位误清。

`ORDER_ACTIVE` 记录只是复位时的退款依据，不参与普通订单准入；只有已经进入 `PREPARED/RESET_WRITTEN` 的真实复位流程才临时禁售。因此普通订单结束后即使清记录时崩溃，也不会把下一单永久卡住。

### 2. 封禁新机械命令并写 999

复用现有紧急复位机械写栅栏，先阻止新的 `in/out/搬盘/丢弃` 命令，再写 `999=1`。

- 写入失败：不退款、不释放当前订单、不冷重启；撤销本次新增的复位栅栏和临时禁售原因，恢复点击前状态并提示重试。
- 写入成功：记录进入 `RESET_WRITTEN`。从此认为旧机械流程已被人工复位终止，不再等待旧动作结果。

### 3. 一次冷重启并释放本地资源

999 成功后安排一次 App 冷重启。新进程识别 `RESET_WRITTEN` 后，在统一状态锁内清理所有旧业务占用：

- 当前订单的 PROCESSING 状态、订单 claim 和 `moveStatus=2`；
- 补肠 session、暂停/续作状态、机械 owner 和匹配资源锁；
- 搬盘、丢弃、人工取肠等运行中的软件占用；
- 复位栅栏之外的旧任务引用和首页“处理中”展示。

这里清的是“谁正在使用机械”的运行态，不删除库存、烤盘有无肠、已完成 `out4` 数量、退款记录、故障记录或物理恢复日志。

为避免现场看到两次启动，新进程若已由系统守护拉起，应取消同一 `resetId` 对应的待执行 Alarm；仓库内仍只保留一个冷重启请求。

若冷重启安排失败，继续保留复位栅栏和临时禁售，提示人工重启 App；不能在旧协程仍存活时提前开放下单。

### 4. HTTP 关闭旧订单

新进程使用设备现有 HTTP 身份调用专用幂等接口。请求包含 `resetId`、设备码、复位类型、订单号及各订单项已确认 `out4` 成功数量。

后端在同一业务收口中完成：

1. 校验设备与已支付订单关系；
2. 以 `max(后端已完成数, 上位机确认的 out4 数)` 作为已交付数，且不得超过订单项总数；
3. 将其余数量标为“人工复位终止、退款处理中”，立即移出运行中订单门禁；
4. owner-safe 释放该订单的 `DEVICE_WORKING_LOCK` 和 processing count，不删除其他订单的新锁；
5. 复用现有退款记录、订单级退款锁和补偿任务发起退款。

`resetId` 用于日志和重试关联，业务幂等复用现有“订单号 + 订单项退款范围”的有效退款记录及订单终态。重复请求重新读取现有结果，不能创建第二笔退款，不需要新增幂等表。若本地订单号缺失，后端只允许收口该设备当前工作锁 owner 或当前唯一的已支付运行中订单；不做全设备历史订单扫描。

HTTP 成功只要求“旧订单已退出下单阻塞、工作锁已释放、退款意图已可靠保存”，不等待微信实际到账。微信暂时失败由现有退款补偿机制继续重试，不能重新占用设备或阻塞下一单。

### 5. 结束复位临时禁售

同时满足以下两项后结束本次临时禁售：

- 距离 999 成功至少 10 秒；
- 后端已确认旧订单不再阻塞，或确认本次没有需要关闭的订单。

结束时只清除 `SYSTEM_RESET_IN_PROGRESS`，恢复点击前保存的 `orderBlockReason` 和原稳定业务状态。普通复位不清原故障；若点击时是订单临时态 `onlineStatus=4`，则按现有订单收口规则退出 4，而不是把设备永久留在“工作中”。紧急复位继续保持维护，等待“检查并恢复设备”。

若 HTTP 暂时失败，机械本地资源仍已释放，但临时禁售记录保留并在新进程/网络恢复后重试。因为此时后台订单和工作锁尚未确认关闭，不能提前开放支付后再让新订单与旧订单冲突。正常网络下该确认应在机械复位的 10 秒窗口内完成。

## 退款口径

- 只有下位机明确返回 `out4` 成功的数量视为已经交付，不退款。
- 在售卖台检测之前失败，全部未完成数量自动退款。
- `out4` 已下发但通信中断、结果未知、未收到成功结果，也按未确认交付退款；接受极小概率“顾客实际拿到且又退款”，以避免顾客未拿到却长期卡单。
- 多商品、多数量按订单项分别计算，只退 `总数量 - 已确认 out4 成功数量`。
- 已退款、退款中或已完成数量不得再次退款。

例如：订单 3 根，前 1 根 `out4` 成功，第二根执行中时人工复位。后端保留第 1 根已完成，另外 2 根自动退款；设备工作锁立即释放，退款到账可以稍后补偿，不影响下一单。

## 业务自检显示

“业务自检”继续读取真实 Modbus 寄存器，不伪造读取失败，也不把 0 或 2 改成其他值。

当 `ResetCloseoutRecord` 尚未结束时，结果顶部明确显示：

> 下位机复位中；以下是当前原始读数，仅供诊断，不代表机械已完成回零。

因此复位期间读到 0、2 或短暂读取失败都可以显示，但不能据此自动判断机械复位完成。复位完成仍以“999 成功后的最短 10 秒窗口 + 后端订单收口确认”为准。

## 最小改动边界

### Android

- 普通/紧急按钮共用一个小型复位协调器，差异只在是否进入维护。
- 新增一个单槽、同步落盘的复位收口记录；当前订单执行时只记录订单号、订单项数量和 `out4` 成功计数，复位时再推进其阶段。它不是普通订单准入门禁。
- 不新增通用订单 outbox、MQTT ACK、后台轮询线程或第二套订单状态机。
- 只在 999 写成功后清运行态；写失败绝不假装复位成功。

### 后端

- 新增一个设备侧 HTTP 收口接口和一个聚合服务；复用现有订单、订单项、退款记录、订单退款锁和工作锁 owner 校验。
- 不新增数据库表，不重构微信支付，不改变正常 MQTT 订单事件语义。
- 增加 `SYSTEM_RESET_IN_PROGRESS` 的后台归一化和“设备复位中，请稍后下单”文案。

### 不清除的事实

- 烤盘/烤肠箱库存与扣减记录；
- 已确认 `out4` 成功数量；
- 搬盘、丢弃、物理状态 journal 和故障审计；
- 原有 `errorStatus`、下平台隔离、算法开关和维护状态；
- 已产生的订单、退款及支付记录。

## 验证与审核门禁

实现必须测试先行，至少覆盖：

1. 普通复位在 `moveStatus=0/1/2/3/4/5` 和寄存器忙时均可写 999，且不改变原业务/故障状态；
2. 999 写失败不清订单、不退钱、不重启，写成功才进入跨进程收口；
3. 复位成功后只安排一次冷重启，守护先拉起时不会再出现第二次可见启动；
4. 本地所有运行资源释放，但库存、烤盘和 journal 保留；
5. 0/1/多商品已确认 `out4` 数量的退款计算正确，未知结果按未交付退款；
6. HTTP 重复请求、App 重启重试、微信退款失败均不重复退款、不恢复工作锁；
7. 工作锁已属于新订单时绝不误删；
8. 后端未确认前保持临时禁售，确认后普通复位恢复原状态、紧急复位保持维护；
9. 自检在复位中显示原始 0/2/读取失败，同时明确“不代表机械回零完成”；
10. 切片1的 `in1~in3` 半故障安全收口和 `in4+` 维护边界全部回归通过。

Android 与后端分别跑定向测试和完整测试，`git diff --check` 必须通过。两个切片完成后，新开 Codex 任务做跨仓整体只读审核；最多两轮，仍有 P1 就停止提交/合入并向用户报告。

本地测试不能代替真机验证。最终仍需在受控设备验证：运营中普通复位、维护中普通复位、订单执行中复位、单次 App 重启、10 秒临时禁售、后续新订单、部分退款和自检原始读数。
