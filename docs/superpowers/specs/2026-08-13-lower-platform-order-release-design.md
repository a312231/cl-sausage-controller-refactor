# 下平台半故障不阻塞上平台售卖设计

## 目标

修复双 lane 补肠在 `in1~in3` 明确失败后残留 session、资源 owner 和 `moveStatus=1`，导致上平台已有熟肠无法出餐，以及下平台已经隔离后订单结束仍错误续补的问题。

本次只修改 Android 上位机控制逻辑，不修改后端、MQTT/HTTP 协议、库存模型、动作寄存器、正常补肠顺序或出餐顺序。

## 已确认根因

当前串行补肠已有 `in1~in3` 安全失败收口，但 `SupplementFailureCloseoutPolicy` 明确排除 `prefetch=true`，双 lane 失败因此保留持久化会话、机械 claim、资源 owner 和 `moveStatus=1`。

订单准入仍允许补肠忙态进入等待；失败会话没有安全收口时，订单最多等待 240 秒。订单收口又会把正常暂停和故障隔离混入同一续作入口；现有续作运行态门禁检查 `onlineStatus/errorStatus/isEnable/Modbus`，没有把 `lowerPlatformStatus=ISOLATED` 和 `supplementEnabled=0` 作为明确的禁止续补条件。

## 设计边界

### 1. 双 lane 故障安全收口

复用现有 session、机械 claim、owner、revision、resourceMask 和持久化证据，不新增锁、session、状态机、配置项或协议字段。

仅当以下条件全部满足时，才允许自动收口：

- 当前是双 lane/prefetch 补肠会话；
- 失败动作属于 `in1~in3`，结果是本次执行观察到的明确下位机错误码，不是通信失败、读取失败、超时或未知结果；
- sessionId、机械 claim revision、当前动作、来源箱、目标盘和资源 mask 完全匹配；
- 没有其他资源 owner、订单出餐 claim、搬盘 journal 或丢弃 journal；
- 没有箱库存扣减、机械取肠、烤盘放置或库存矛盾证据；
- 按当前协议读取动作状态，取得连续稳定的安全终态证据，不存在 `RUNNING` 或其他动作残留。

满足条件后，按现有 owner/revision 的 CAS 路径一次性完成：关闭该失败补肠会话、释放匹配的机械 claim、释放该 owner 持有的 `BOTTOM+LIFT+ABOVE` 资源，并仅在 claim 仍属于该会话且 `moveStatus==1` 时恢复空闲。不得直接赋值 `moveStatus=0`，不得调用全局清锁。

下平台继续保持 `ISOLATED`、`supplementEnabled=0`，不自动恢复补肠；上平台正常烤制、保温和售卖。

### 2. 动作差异

- `in1` 明确失败：只要没有取肠或库存变化证据，允许按上述条件安全收口。
- `in2=0x00E5`：确认未取到肠且未扣库存时，按原有箱级降级/候选箱规则处理；若下平台已进入整个平台隔离，则关闭本次失败会话，不再切箱续补。
- 其他 `in2` 失败：只有明确证明未取肠、未扣库存才允许收口。
- `in3` 失败：通常 `in2` 已完成并已经取肠、扣库存，默认不允许自动释放；只有证据明确证明没有任何物理提交时才可能进入安全收口。
- `in4~in7`：不纳入本次自动释放，继续保持现有强安全收口和人工处理要求。

### 3. 隔离态禁止错误续补

订单结束、运行态恢复和重启恢复的双 lane 续作入口统一增加同一条门禁：只要 `lowerPlatformStatus=ISOLATED` 或 `supplementEnabled=0`，就禁止下发任何 `in1~in7` 续作。

若失败会话已按第 1 节安全收口，订单可以直接获取售卖所需资源并执行 `out1~out5`。若证据不足无法安全收口，则保留原 session/owner/claim 和 `moveStatus=1` 作为现场证据，并使用已有 `LOWER_PLATFORM_RECOVERY_REQUIRED` 阻止新订单付款，避免顾客付款后等待 240 秒。

### 4. 并发与资源原则

- 释放必须匹配 sessionId、claim revision、owner 和 resourceMask；任一项变化即停止释放。
- 如果订单已经取得 `moveStatus=2` 或售卖资源，补肠故障路径不得覆盖订单状态或释放订单资源。
- 不创建用于“等待释放”的额外 session、全局锁或后台任务。
- 正常的订单暂停补肠、出餐完成后续补行为保持不变；只有故障隔离态被禁止续补。
- 正常 `out1~out5` 一旦开始，补肠不得抢占其资源。

## 修复前后示例

### 本次 `in1=0x00EE`

修复前：下平台隔离，但双 lane session、资源和 `moveStatus=1` 残留；订单被接受后一直等待，随后还可能错误续跑 `in2/in3`。

修复后：确认本次 `in1` 明确失败、没有取肠/扣库存、动作状态连续稳定后，精准关闭失败会话并释放它自己的资源；下平台仍隔离，已有熟肠立即允许执行 `out1~out5`。

### `in3` 失败且 `in2` 已成功

修复前：可能卡住，也可能被错误当作可续作状态。

修复后：因为已有取肠和扣库存证据，保留 session、owner、claim 和忙态，阻止新付款并提示人工处理；不清锁、不继续售卖、不重放 `in2`。

## 验证与审核

实现严格按测试先行：

1. 先增加回归测试，复现双 lane `in1=0x00EE` 安全终态仍残留资源，以及隔离态订单结束错误续补；确认测试在现有代码上失败。
2. 最小实现双 lane 安全收口与隔离续作门禁，确认定向测试转绿。
3. 覆盖 `in2` 无扣库存、`in3` 已扣库存、Modbus/结果未知、owner/revision/mask 不匹配、订单已持有 `moveStatus=2` 等拒绝路径。
4. 运行 Android 完整单元测试和 `git diff --check`。
5. 使用 fresh Codex 独立只读审核方案和 diff；最多两轮，存在未解决 P1 即停止，不提交发布。

本地测试只能证明控制逻辑和状态不变量，不能替代真机 Modbus、机械位置和真实扫码出餐验证。实现完成后仍需在受控设备验证：`in1` 明确失败、下平台隔离、资源及时释放、上平台成功出餐、隔离期间没有任何 `in` 续作。
