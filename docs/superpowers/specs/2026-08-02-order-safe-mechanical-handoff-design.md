# 订单优先与机械动作安全交接设计

## 目标

订单到达时不硬中断已经下发的机械命令；当前动作到达安全终态后让整单出餐优先。订单成功后继续剩余自动任务，订单失败或状态未知时进入维护并保留恢复证据。

## 范围

- 修复非并行多目标补肠在 `Paused("in7")` 后未释放 owner、资源锁和 `moveStatus` 的问题。
- 并行补肠仅在订单完整成功后执行 `Ready` 或 `ReplanRemaining` 续作。
- 非并行补肠仅在订单完整成功后恢复 `in1~in3` 暂停根；`in7` 已完成根不重放，只保留批次剩余目标等待调度。
- 自动丢弃在每根动作开始前重新检查订单和自动调度门禁，避免订单到达或订单失败转维护后继续下一根。
- 自动搬盘和自动丢弃共用现有 `faultHeatTransitionLock` 完成短时命令准入：锁内只检查订单、owner、`moveStatus` 并持久化 `COMMAND_INTENT`；Modbus、延时、资源锁和终态轮询均在锁外。
- 正常营业、允许下单期间不启动自清洁。保留维护/停业场景的底层清洁能力；当前 4F no-op 语义不变。
- 双 lane 在控制器内默认开启；全量配置仅显式整数 `0/1` 覆盖，字段缺失或非法时保持当前值。本次不修改后端、协议或数据库默认值。

## 安全节点

- 补肠：订单在 `in4` 提交前获得控制权时停在 `in1~in3`；`in4` 已提交后完成当前根到 `in7`。
- 搬盘：寄存器 202 未下发前允许订单获得控制权；下发后等待 203 明确终态。
- 丢弃：`PREPARED` 可安全释放；`COMMAND_INTENT` 或 `COMMAND_ISSUED` 后等待本根明确终态，结果未知时进入维护并保留证据。
- 出餐：整单期间保持 `onlineStatus=4`、`moveStatus=2`，自动机械调度不得插入各根出餐之间。
- 自清洁：仅非营业、不可下单且机械空闲时允许启动；已下发命令仍按终态确认规则收口。

## 状态与恢复

- 订单结果使用 `SUCCESS`、`FAILED`、`UNKNOWN` 三态。
- `SUCCESS`：清理订单暂停标记，恢复暂停根或释放已完成根，并由正常调度继续剩余批次。
- `SUCCESS` 但补肠续作返回失败：顾客订单仍成功，设备进入维护并保留剩余批次和恢复证据。
- 旧订单收口时若已有后续订单接管暂停标记，不启动补肠，也不把“为后续订单继续暂停”误判为续作失败。
- `FAILED`：设备保持/进入维护，不调用补肠续作；已暂停会话、批次意图和机械 journal 保留。
- `UNKNOWN`：按比失败更保守的方式处理，保持 owner、锁、`moveStatus` 和 durable evidence，不自动清零。
- `COMMAND_INTENT` 之后出现取消、写失败或普通异常：统一进入维护并保留 owner、journal 和 `moveStatus`。
- 通用 owner 协调器只负责 owner 与 `moveStatus` 的原子认领/释放；物理终态和订单结果由调用方安全收口策略验证。

## 测试

- 非并行多目标：A 在 `in4~in7` 收到订单，A 完成后释放资源，B/C 不在订单前启动。
- 非并行暂停根：A 在 `in1~in3` 暂停，订单成功后从对应检查点恢复。
- 并行完成根：订单成功后允许 `moveStatus=2` 的 `ReplanRemaining` 收口；失败/未知时拒绝。
- 自动丢弃：订单到达或状态转维护后不启动下一根。
- 自清洁：`onlineStatus=1/4` 拒绝，停业或维护且机械空闲时才允许。
- 完整 Debug 单测与 Debug APK 构建；真机 RS485/Modbus 验证另行执行。
