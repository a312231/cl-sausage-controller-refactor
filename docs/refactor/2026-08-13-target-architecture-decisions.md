# 上位机重构目标与架构决策

日期：2026-08-13
依据：用户当前选择；后续若业务口径变化，以新的明确决定更新本文件。

## 已确认目标

1. UI 不要求保持现状，可以重新设计；目标是简单、易用、状态和下一步操作一眼可懂。
2. 下位机协议、Modbus 寄存器地址和现有动作指令保持兼容，第一阶段不修改下位机。
3. 有专用测试设备、测试 MQTT Broker 和测试后端，可用于后续真实联调。
4. 优先解决：
   - 偶发故障难恢复；
   - 调度算法难调整。
5. 采用绞杀式渐进重构，不以一次性重写替代现有可运行系统。

## 断网业务边界（待用户确认最后一句）

建议边界：

- 断网后不接受新订单，不开始未确认付款的出餐；
- 已付款但设备尚未收到的订单，由服务端在恢复连接后按现有幂等规则重发，设备不得自行猜测；
- 设备已经接收并开始执行的已付款订单，不因断网中断机械动作，应在本机安全完成或进入可恢复的安全收口；
- 烤制、保温、必要补货、故障保护和本地恢复属于设备自治能力，可在断网时继续；
- 联网后补报订单执行、库存、烤盘和设备最终状态；
- 断网期间二维码/可下单状态必须隐藏或被后端阻断，避免顾客进入无法履约的支付流程。

待确认：是否接受“已收到且已经开始执行的已付款订单，断网后仍应本地完成或安全收口”。

## 目标分层

### 1. 纯业务核心

- 调度策略、可售判定、补货计划、模式切换条件；
- 只接收不可变输入并返回决定；
- 不依赖 Android、UI、MQTT、HTTP、Modbus、数据库和系统时钟。
- 调度算法通过稳定 ID 和统一策略接口注册，允许算法 A/B/C 并存；选择算法不修改订单或机械代码。
- 未知算法 ID 不得静默回退；真实新算法必须有独立规则、自动化差分/场景测试和灰度证据。
- 算法选择由应用编排层的策略目录完成，配置只保存稳定 ID；策略实现不能读取/修改 Android Context、UI、MQTT、库存仓库或硬件端口，只接收不可变业务快照并返回候选决定。
- 运行中不得热切算法：只有设备空闲、无 active order、无整单 claim、无单根 session、无补货/清洁/维护 owner 时才允许 A/B 切换；已开始的流程固定使用开始时记录的策略 ID/版本，切换失败保持原策略并进入诊断，不临时换算法续作。
- 纯 JVM 1C-1 曾用可售候选单一子策略建立严格 ID、未知 ID fail-closed、七项运行时阻断和 pin 的初步模型；1D-1 已将该部分模型替换为完整 `SchedulerProfile` 级目录、pin 和切换计划，避免把一个子策略误称为整套算法。
- 纯 JVM 1C-2 已把“目标、库存、占用和可分配位置均已确定后的补货口味混配”抽为 `SupplementTasteMixStrategy`，算法 A 的稳定 ID 为 `relative-deficit-taste-mix-v1`；App 只保留兼容适配，低峰/高峰目标、批次和位置仍由旧流程拥有。该子策略不等于完整调度 profile，当前不得在 UI 中伪装成整机算法 A/B。
- 纯 JVM 1C-3 已把两种补货目标配额规则抽为 `SupplementTargetAllocationStrategy`，算法 A 的稳定 ID 为 `inventory-proportional-target-v1`；App 继续拥有补货开关、库存/口味/IR错误/源箱位安全过滤、Int 聚合和日志，核心不能重新纳入被排除库存。六个旧调用点保持，不新增子策略选择 UI。
- 纯 JVM 1C-4 已把低并发补 13~15/16~18/关 2 区决策、高并发稳态 9 坑位门槛及对安全候选位置的有序配对抽为 `SupplementBatchHeatPositionStrategy`，算法 A 的稳定 ID 为 `legacy-fixed-batch-heat-position-v1`。pending/恢复/初始化/过保收口优先级、候选安全过滤、执行前复核、温控和机械动作继续由 App 拥有；低热仍保留库存只覆盖 1~2 根时的部分批次基线语义。高热先计算不修改烤盘的旧预填口味计划，每条延迟写入携带预期对象身份、位置和目标口味；提交前确认对象、位置、占用和空白口味均未漂移，全量校验通过后按“预填 -> planner 覆盖”旧顺序提交，非法计划不得污染烤盘状态。
- 纯 JVM 1C-5 已把“低并发何时申请转高并发、高并发何时申请转低并发”抽为 `TrafficDemandTransitionStrategy`，算法 A 的稳定 ID 为 `legacy-demand-timeout-transition-v1`。App 继续拥有调度/库存/稳态门禁、首次计时锚点、合法单向过渡、恢复/回搬/清残、配置持久化和 runtime_state 上报；策略只返回方向固定的候选 outcome，错误方向结果必须 fail-closed。为保证本切片不改变 2.5.42，分钟换算的 Int 回绕、Long 差值回绕和严格比较暂按原行为冻结，安全归一化须另开授权切片。
- 纯 JVM/App 1D-1 已建立完整 `SchedulerProfile A`，稳定 ID 为 `legacy-scheduler-profile-a-v1`，原子绑定上述五类已迁移子策略；App 的 8 个直接构造点改为读取同一个进程期固定 A。任意组装工厂只接受 `test-` ID，正式 B/C 必须新增各自受控工厂。当前没有真实 B/C、配置字段、UI、持久化或运行时切换；可售候选仍只在默认关闭影子路径，legacy 候选仍是机械权威。
- App 1D-2 已建立唯一只读的 Profile 切换就绪证据入口，直接消费现有配置缓存、订单、claim、动作 session、补货/清洁/维护 owner、journal、fence 和资源锁，不复制第二套业务状态。结果严格区分 `AVAILABLE`、`BLOCKED`、`UNAVAILABLE`；配置未初始化或任一关键证据损坏/读取失败即 fail-closed。该采样非原子且没有激活权，不能被 UI、MQTT 或调用方当成切换授权；真实激活仍属于 1D-3。
- 真正可选择的 `SchedulerProfile A/B` 必须原子绑定售卖候选、补货目标比例、批次数量/热源/位置、口味混配和模式切换等已完成迁移的子策略版本，避免把不同版本随意拼装成未经验证的组合。
- 新算法先离线回放和影子比对，再小范围启用；影子算法只有指标输出权，没有库存写权、状态写权或机械动作权。

### 2. 应用编排层

- 订单履约、补货、自清洁、维护恢复等用例；
- 管理状态机、checkpoint 和超时，但不直接操作串口或界面；
- 明确每个流程的开始条件、当前 owner、终态和恢复入口。

### 3. 状态与恢复层

- 统一拥有烤盘、箱位、订单执行、动作会话和恢复 checkpoint；
- 区分“期望状态”“已下发动作”“下位机结果”“已持久化终态”；
- 重启后只依据可验证 checkpoint 恢复，不根据 UI 或陈旧寄存器猜测。
- 纯 JVM 2C-1 已把断电冷启动三分支和 60 秒运行心跳是否到期提取为确定性决策；App 继续拥有墙钟、journal、烤盘/config 变更、持久化、日志及 MQTT/HTTP，真实断电恢复效果仍须真机验证。
- 纯 JVM/App 2C-2 已把故障停热后的烤制顺延、保温到期、食品安全待丢弃和 fail-closed 候选判断提取为 `FaultHeatPauseAdjustmentPolicy`。核心只接收调用方提供的时间、归一化阈值和不可变烤盘快照；App 继续拥有墙钟、`KaoPan/AppConfig`、journal、持久化、日志、状态同步和温控恢复顺序。当前只完成源码/JVM/Debug 构建验证，真实断电、温控、MQTT、RS485/Modbus 和机械效果仍须测试设备联调。

### 4. 端口与适配器

- `MechanicalPort`：包装现有 Modbus/RS485 和动作组，不改变下位机协议；
- `OrderPort`：接收已确认订单和回执；
- `TelemetryPort`：MQTT 主通道与 HTTP 补偿；
- `InventoryStore`：烤盘、箱位和持久化；
- `Clock`：业务时间由外部注入；
- 端口必须窄，只暴露业务需要的动作和结果，不把全局单例泄漏进核心。

### 5. UI 展示层

- 首页只突出：能否售卖、当前动作、预计等待、故障及处理建议；
- 维护页按“现象—原因—可执行操作—风险”展示；
- UI 不直接改库存、机械 owner 或动作状态，只发送明确用户意图。

## 可靠性和安全原则

- 纯策略输出是候选，不是机械授权；机械动作前必须保留最新状态复核。
- 同一机械资源同一时刻只能有一个明确 owner/session。
- 任何动作必须有可识别终态：成功、明确失败、证据未知；证据未知不得伪装成成功。
- 网络、日志、UI 和影子算法失败不得中断正在安全执行的机械动作。
- 每个重构切片默认关闭或不接运行路径，先测试、影子验证，再切换。
- JVM 测试、APK 构建、测试 Broker 和真实 RS485/机械证据分别记录，不互相替代。

## 长期防偏航门禁

以下规则用于减少重复讨论和返工；只保留能通过代码、测试或验证记录检查的约束，不把易变化的现场参数写入 `AGENTS.md`：

1. “算法 A/B/C 可选择”只指完整 `SchedulerProfile`；零散子策略、布尔开关或 UI 文案不得冒充完整算法切换。
2. Profile 必须原子绑定全部已迁移子策略的稳定 ID/版本；缺项、未知 ID 或不兼容组合必须拒绝激活并保留原 profile，不允许运行时临时拼装。
3. 订单、单根履约、补货、清洁、维护或机械 owner/session 已开始后固定原 profile；仅在明确安全空闲点允许原子切换，失败不改变当前选择。
4. 纯核心只接收不可变快照并返回计划/候选请求；时钟、随机数、库存和硬件通过窄输入/端口提供，核心不得直接读 Android、MQTT/HTTP、文件/数据库、Modbus/RS485 或全局单例。
5. App 安全状态机始终拥有最终否决权；策略不得直接写配置/库存/烤盘、发布消息或触发机械动作，执行前必须用最新状态复核。
6. 新算法按“离线回放 -> 默认关闭影子比对 -> 人工安全选择 -> 现场灰度”推进；远程选择属于后续能力，不能绕过本地空闲门禁和回退边界。
7. 每个切片采用分层验证：先目标模块/定向测试，达到阶段边界后再跑全仓 `test` 和构建；无高风险边界变化时不得机械地重复昂贵全仓验证。
8. 交付必须分别报告源码静态、JVM、构建、测试 MQTT、真实 RS485/Modbus/温控/机械证据；后四类未执行时必须明确标注，不允许以 APK 或单测代替。
9. 下位机寄存器、RS485/Modbus 语义和既有 MQTT/HTTP 契约默认保持兼容；任何协议变化必须单独立项、版本化并获得明确授权，不能夹带在内部重构切片中。
10. Handler、线程、协程、Timer/Executor、MQTT/串口连接、监听器、WakeLock、媒体和文件资源必须有唯一生命周期 owner、幂等 start/stop 与可验证释放路径；禁止靠静态 Context 或无界后台任务维持业务状态。
11. 订单扣减、库存变更和机械动作等不可逆边界必须保留唯一 operation/session/owner、动作前 checkpoint 和幂等恢复依据；调度策略只产出意图，不能绕过这些边界直接执行副作用。

## 推荐顺序

1. 可售候选纯策略：建立核心模块边界和差分测试方法；
2. 故障/恢复状态盘点：把动作 checkpoint、owner、下位机结果和恢复入口画成可验证状态图；
3. 选一个最常见、证据最完整的故障恢复流程做第二个绞杀切片；
4. 逐步抽离补货和模式切换策略；
5. 再抽机械动作编排端口与恢复协调器；
6. 最后处理 MQTT/HTTP 适配、UI 重做和历史遗留资源清理。

MQTT 5 不作为上述步骤的前置条件，单独立项评估。
